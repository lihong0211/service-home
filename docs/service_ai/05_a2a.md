# Agent-to-Agent 协议层（A2A）

> 文件：`service/ai/a2a/`（orchestrator.py、host_agent.py、registry.py、schemas.py、run_orchestrator_api.py、agents/）
> 子智能体自动启动：`app/factory.py`（lifespan）
> 全量重写日期：2026-08-18

---

## 第一部分：背景演进

**单体 Agent 的局限**

一个 Agent 把"理解意图 → 检索/推理 → 生成 → 校验"全部塞进一次 LLM 调用或一条 Prompt 链，能应付简单任务，但复杂任务（如"主题 → 大纲 → 正文 → 摘要"这类多阶段内容生产）会遇到三个问题：Prompt 越堆越长导致注意力稀释；单点故障——一步出错整条链路重来；无法独立扩展某一环节（比如正文生成需要更强模型、更长超时，而摘要只需要一个轻量模型）。业界的解法是把任务拆给多个专职 Agent 协作，而不是让一个 Agent 包打天下。

**Google A2A Protocol 简介**

Agent-to-Agent Protocol（Google，2025）试图标准化 Agent 之间"怎么互相发现、怎么互相调用"这件事，类比于微服务领域的 OpenAPI + HTTP：只要双方都遵守协议，Agent 可以用不同语言、不同框架实现，仍能互相协作，不需要为每一对 Agent 单独定制接口。

核心概念：

- **Agent Card（智能体名片）**：`GET /.well-known/agent.json` 暴露的能力描述——name、description、skills、capabilities，供调用方在运行时发现"这个 Agent 能干什么"。
- **Task（任务）**：协议的核心执行单元，具有明确生命周期 `submitted → working → input-required → completed/failed/canceled`（见 `schemas.py` 的 `TaskState`）。
- **Message / Part**：`Message.parts` 是一个 `TextPart | FilePart | DataPart` 的列表，是 Agent 之间传递输入输出的最小单位；`DataPart` 承载结构化 JSON，是链式任务里最常用的载体。
- **Artifact（工件）**：Agent 完成任务后通过 `Task.artifacts` 返回的产出物，下一个 Agent 的输入直接来自上一个 Agent 的 artifact。

**演进脉络**

| 阶段 | 方案 | 问题 |
|------|------|------|
| 自定义 API | 每对 Agent 私有接口 | 新增 Agent 要改所有下游代码 |
| 同进程编排（如 LangGraph StateGraph） | 单进程内多节点顺序执行 | 无法独立部署/扩展某一步骤，一步阻塞全链路阻塞 |
| 工具调用（Function Calling）→ 子 Agent | 主 Agent 用工具形式"调用"子 Agent | 子 Agent 本质仍是函数，没有独立的任务状态机和生命周期 |
| **A2A Protocol** | Agent Card 发现 + Task 生命周期 + 标准 HTTP | Agent 可独立进程/独立端口部署，具备统一的暂停-续跑语义（`input-required`） |

**本模块的定位**

本模块是 A2A 协议在一个"主题 → 风格确认 → 大纲 → 正文 → 摘要"内容生产流水线上的落地：四个子 Agent（`StyleAgent`、`OutlineAgent`、`DocAgent`、`SummaryAgent`）各自是独立 FastAPI 进程，通过标准 A2A 接口对外暴露；`orchestrator.py` 是 Client Agent（编排器），`host_agent.py` 是其中负责"下一步调哪个 Agent"的动态路由决策模块；两者共同构成一个具备人机协作（Human-in-the-loop）能力的 A2A 编排链。与旧版实现相比，最大的架构变化是路由从"写死的三步顺序"演进为"LLM 驱动的动态路由"，详见变更记录。

## 第二部分：架构剖析

**整体分层**

| 模块 | 文件 | 职责 |
|------|------|------|
| Client Agent / 编排器 | `orchestrator.py` | 驱动整条链：调用 `registry.discover` 做能力发现、调用 `host_agent.decide_next_agent` 决定下一步、通过 `httpx` 向子 Agent 发 `POST /tasks/send`、维护暂停/续跑状态、把结果转成同步 JSON 或 SSE 流 |
| Host Agent | `host_agent.py` | 只负责一件事：`decide_next_agent(topic, completed_agents, latest_data)` —— 结合目标、已发现 Agent 的技能描述、已完成步骤，问本地 LLM（Ollama `deepseek-r1:1.5b`）"下一步该调谁"，解析失败时退化为固定顺序 `_FALLBACK_ORDER` |
| Registry | `registry.py` | 维护 `AGENT_BASE_URLS`（Agent 名 → base URL 的静态映射）；`discover`/`discover_all` 拉取并缓存各 Agent 的 `AgentCard` |
| Schemas | `schemas.py` | Pydantic 定义的 A2A 协议类型：`Part` 三态联合、`Message`、`Task`/`TaskStatus`、`AgentCard`、以及编排器自用的 `ChainStep`/`OrchestrationResult` |
| 子智能体 | `agents/style_agent.py`、`outline_agent.py`、`doc_agent.py`、`summary_agent.py` | 各自是独立 FastAPI app，暴露 `GET /.well-known/agent.json`、`POST /tasks/send`、`GET /tasks/{task_id}`，用进程内 `dict` 存 Task |
| 对外 API | `run_orchestrator_api.py` | 可独立运行的编排器 HTTP 服务（默认 8010），复用 `orchestrator.get_result_for_frontend`；生产环境中实际是通过 `routes/ai.py` 挂到主服务的 `/ai/a2a/*` |

**host_agent.py 与 orchestrator.py 的关系**

`host_agent.py` 不是一个独立运行的"宿主智能体"服务（它没有 FastAPI app，不监听端口），而是 `orchestrator.py` 内联依赖的一个**决策函数模块**，扮演 A2A 术语里 Host Agent 的角色——即"决定调用哪个远程 Agent"的那一层逻辑。`orchestrator.ChainRun.run_events()` 每轮循环都调用 `decide_next_agent()` 取得下一个 agent 名，再由 `orchestrator._call_step()` 完成真正的 A2A 调用（`_send_message_with_retry` → `POST /tasks/send`）。这是一次关注点分离式重构：`orchestrator.py` 只管"怎么调、怎么重试、怎么暂停续跑"（编排机制），`host_agent.py` 只管"该调谁"（编排策略），策略部分可以独立替换（例如换成规则引擎或更大的模型）而不影响调用机制。

**核心数据流：一次跨 Agent 任务的完整路径**

```
用户 POST /ai/a2a/chain  {topic: "..."}
        │
        ▼
routes/ai.py → a2a_chain_api(request)  [进程：主服务，如 :3000]
        │
        ▼
orchestrator.get_result_for_frontend(topic)
        │
        ▼
ChainRun(topic).run_events()  ── while len(completed_agents) < MAX_STEPS(5):
        │
        ├─► host_agent.decide_next_agent(topic, completed_agents, latest_data)
        │       │
        │       ├─ registry.discover_all() → 依次 GET http://127.0.0.1:800{1..4}/.well-known/agent.json
        │       │     （跨进程 HTTP 调用，子智能体运行在各自的独立进程里）
        │       └─ 调用本地 Ollama（POST http://localhost:11434/api/chat）选出下一个 agent，
        │          或退化为 _FALLBACK_ORDER = [StyleAgent, OutlineAgent, DocAgent, SummaryAgent]
        │
        ├─► orchestrator._call_step(next_agent, parts)
        │       │
        │       ├─ registry.discover(agent_name)          能力发现（非续跑步骤才做）
        │       ├─ _send_message_with_retry(agent_name, Message)
        │       │     └─ httpx.AsyncClient.post(f"{agent_url}/tasks/send", json=...)
        │       │        （跨进程 HTTP 调用，超时 600s，失败按 _RETRY_ATTEMPTS=2 退避重试）
        │       └─ 子智能体进程内处理请求，返回 Task
        │             ├─ state == "input-required" → 记录 PausedSession，链路挂起，
        │             │    等待前端调用 POST /ai/a2a/chain/resume 携带 context_id + answer 续跑
        │             ├─ state == "completed" → 从 Task.artifacts[0].parts 中取出 DataPart.data，
        │             │    作为 latest_data 传给下一轮 decide_next_agent + 下一个 Agent 的 DataPart 输入
        │             └─ 其它/异常 → 该步 status="failed"，链路提前终止（已完成步骤的产出保留）
        │
        └─► 循环直到 decide_next_agent 返回 "DONE" 或达到 MAX_STEPS
        │
        ▼
OrchestrationResult{chain, tasks, final_task} → JSONResponse（同步）
                                              → 或每步一条 SSE `data: {...}\n\n`（流式，a2a_chain_stream_api）
```

进程间通信方式：编排器进程与四个子智能体进程之间**全部通过 HTTP/JSON**（`httpx` 异步客户端 + `requests` 同步客户端），没有共享内存、没有消息队列；`orchestrator.py` 内的 `_paused_sessions: dict[str, PausedSession]` 和各子智能体内的 `_tasks: dict[str, Task]` 都是**进程内内存状态**，重启对应进程即丢失（代码注释里也明确标注"生产建议换为 Redis/DB"）。

**关键设计原则**

- **能力发现驱动路由**：Host Agent 不是硬编码"先 Style 再 Outline"，而是把 `registry.discover_all()` 拿到的 `AgentCard.description` 喂给 LLM 做决策，新增/替换 Agent 只需要改 `registry.AGENT_BASE_URLS`，不需要改路由代码。
- **协议层用 Pydantic 强类型约束，业务数据层保持弱类型**：`Task`/`Message`/`AgentCard` 是强类型 Pydantic 模型，保证协议字段合规；但 `DataPart.data: dict[str, Any]` 是任意 JSON，Agent 间的业务字段约定（如 `topic`、`title`）是隐式契约。
- **暂停/续跑是一等状态而非异常**：`input-required` 是 `TaskState` 枚举里的正常状态之一，`ChainRun` 显式区分"续跑"（`_resume_agent` 非空）与"新一轮路由决策"两条路径，都复用同一个 `_call_step`，没有另写一套续跑逻辑。
- **失败降级而非硬失败**：`_send_message_with_retry` 重试耗尽后该步标记 `failed`，但 `run_events()` 直接 `return`，已产出的 `chain`/`tasks` 数据保留在返回结果里，不因为最后一步失败就丢弃前面几步的产出。

**与行业标准方案对比**

| 维度 | Google A2A（本模块） | OpenAI Swarm/Agents SDK | AutoGen（Microsoft） | LangGraph 多节点 |
|------|----------------------|--------------------------|----------------------|-------------------|
| 部署形态 | 每个 Agent 独立进程/端口，HTTP 通信 | 同进程内 handoff，函数级切换 | 同进程内多 Agent 对话循环（可扩展分布式） | 同进程内 StateGraph 节点 |
| 通信协议 | 标准化 HTTP + JSON（Agent Card / Task） | 无跨进程协议，Python 对象直接传递 | 消息传递抽象（ChatMessage），无强制线协议 | 内部状态字典，无网络协议 |
| 任务状态机 | `TaskState` 显式枚举，含 `input-required` 暂停态 | 无正式状态机，靠会话变量 | 有对话轮次但无标准化 Task 生命周期 | `StateGraph` 节点间状态传递，无跨进程持久化 |
| 跨语言互操作 | 是（只要实现 HTTP 接口即可接入，与语言无关） | 否（Python only） | 否（Python/`.NET` 各自实现，非互操作） | 否（Python only） |
| 独立扩缩容 | 是（每个 Agent 可单独加机器/加进程） | 否（进程内共享资源） | 部分（分布式 AutoGen 需要额外基础设施） | 否 |
| 运维复杂度 | 高（多进程、多端口、需要进程守护） | 低（单进程） | 中 | 低（单进程） |

**选型建议**：需要多团队/多语言独立开发和部署 Agent、或希望单个 Agent 故障不拖垮全局时选 A2A（本模块的实现方式）；若所有 Agent 都由同一团队用 Python 维护、追求开发和调试效率、不需要独立扩缩容，Swarm/AutoGen/LangGraph 这类同进程方案启动更快、调试更简单、没有端口管理和网络超时的负担。

## 第三部分：代码实现深度解析

**核心函数/类清单**

| 名称 | 文件 | 作用 |
|------|------|------|
| `ChainRun`（类，含 `run_events()`） | `orchestrator.py` | 一次链路执行的状态载体；`run_events()` 是唯一的执行入口，同步/SSE 两种对外形态都消费它产出的事件序列 |
| `decide_next_agent(topic, completed_agents, latest_data)` | `host_agent.py` | Host Agent 路由决策：LLM 选择 + `_fallback_next` 兜底 |
| `_send_message_with_retry(agent_name, message)` | `orchestrator.py` | 对 `_send_message` 的重试封装，`_RETRY_ATTEMPTS=2` 次，指数退避 `_RETRY_BACKOFF_SECONDS * (attempt+1)` |
| `_call_step(agent_name, parts, is_resume, resume_task_id)` | `orchestrator.py`（`ChainRun` 方法） | 单步调用的完整处理：发现能力 → 发消息 → 解析 Task 状态 → 产出 `step_start`/`step_done`/`chain_paused`/`chain_error` 事件 |
| `discover_all()` / `discover(agent_name, force)` | `registry.py` | 能力发现；`discover` 内部有 `_card_cache` 缓存，`discover_all` 对单个不可达 Agent 静默跳过 |
| `run_chain(topic)` / `resume_chain(context_id, answer)` | `orchestrator.py` | 同步执行入口：分别对应"发起新链路"和"续跑暂停链路"，都是对 `ChainRun.run_events()` 的消费封装 |
| `stream_chain(topic)` | `orchestrator.py` | SSE 生成器，把内部事件字典的 `"type"` 字段映射为线上协议的 `"event"` 字段后逐条 yield |
| `lifespan(app)` | `app/factory.py` | 应用启动时以子进程方式拉起四个子智能体（8001-8004），并在启动前 `_kill_stale_listener` 清理残留监听进程 |

**Task 生命周期管理**

`schemas.TaskState` 定义了 `submitted | working | input-required | completed | failed | canceled` 六态。本模块实际路径只经过其中三种终态相关分支：

- 正常完成：子智能体在 `_process()` 里直接把 `Task.status.state` 置为 `"completed"`（四个子 Agent 目前都是同步处理，没有真正落到 `working` 中间态）。
- 需要人工输入：`StyleAgent._process()` 首次调用时不产出 artifact，直接返回 `state="input-required"`，并把 `Task` 存入自己进程内的 `_tasks` 字典；`orchestrator._call_step` 检测到该状态后，把整条链路的现场（`chain`、`tasks`、`completed_agents`、`latest_data`、`paused_agent`、`paused_task_id`）打包进 `PausedSession`，存进模块级字典 `_paused_sessions`，然后向调用方返回 `chain_paused` 事件/状态。
- 续跑：`POST /ai/a2a/chain/resume` → `resume_chain(context_id, answer)` 从 `_paused_sessions` 弹出对应 `PausedSession`，`ChainRun.from_paused()` 重建执行状态，续跑时 `Message.taskId` 显式带上原 `paused_task_id`，子智能体（如 `StyleAgent`）据此识别"这是对同一个 `input-required` 任务的回答"而不是新任务，在 `_process()` 里进入续接分支，把状态从 `input-required` 扭转为 `completed` 并挂上 artifact。
- 失败：`httpx.HTTPError` 重试耗尽，或 `task.status.state` 既不是 `completed` 也不是 `input-required`（例如子智能体返回了 `failed`，或 `completed` 但没有可提取的 `DataPart`），`_call_step` 把该 `ChainStep.status` 标记 `"failed"`，写入 `self.final_task`，产出 `chain_error` 事件，`run_events()` 判断最后一个事件不是 `step_done` 就提前 `return`，终止主循环。

**多进程/多端口架构**

`app/factory.py` 的 `lifespan()` 在应用启动阶段，对 `service/ai/a2a/agents/` 下的四个脚本分别 `subprocess.Popen([sys.executable, script], cwd=root)`，端口依次是 `8001（Outline）/8002（Doc）/8003（Summary）/8004（Style）`，启动前先用 `_kill_stale_listener(port)`（`lsof -ti :{port}` + `SIGTERM`）清理残留进程，确保每次重启主服务都用最新代码跑子智能体。每个子智能体脚本自身是可以独立执行的 FastAPI app（`if __name__ == "__main__": uvicorn.run(app, ...)`），既能被主服务拉起，也能单独 `python service/ai/a2a/agents/outline_agent.py` 手动跑起来调试。编排器与主服务运行在同一个进程/端口（通过 `routes/ai.py` 挂载 `/ai/a2a/*`），只有四个子智能体是独立子进程；`run_orchestrator_api.py` 则是编排器本身的一个可独立部署版本（默认监听 8010），用于不依赖主服务、单独跑通整条链路的场景。

**设计决策与取舍**

1. **为什么用独立进程而不是同进程多线程/协程**：A2A 协议的初衷就是让每个 Agent 可以独立开发、独立扩展、独立故障隔离——如果四个 Agent 跑在同一个进程里，即使用协程并发，也依然共享同一个 Python 解释器和内存空间，一个 Agent 里的死循环、内存暴涨或未捕获的段错误会拖垮全部 Agent；用独立进程 + HTTP 通信，`_kill_stale_listener` 甚至可以在某个子智能体卡死时单独 `kill -9` 重启，不影响主服务和其它子智能体。代价是显式的网络往返开销和"进程活着但没监听端口"这类边缘故障需要额外处理（本模块目前靠 `discover_all()` 里的 `try/except` 跳过不可达 Agent 来兜底，而不是做健康检查）。
2. **为什么路由决策（host_agent）从固定顺序改成 LLM 动态选择**：固定顺序（Style→Outline→Doc→Summary）没法应对"某些主题不需要先问风格"或"未来新增一个 Agent 插入到链路中间"这类场景；把决策权交给 `decide_next_agent`，新增 Agent 只需要在 `registry.AGENT_BASE_URLS` 里加一行、写好 `AgentCard.description`，不需要碰 `orchestrator.py`。代价是路由结果依赖本地小模型（`deepseek-r1:1.5b`）的输出稳定性，因此必须有 `_fallback_next` 兜底：LLM 不可用、超时、输出无法解析、或选择了已完成过的 Agent 时统一退化为 `_FALLBACK_ORDER` 固定顺序，保证行为可预测、不会死循环或跳步。
3. **为什么暂停态用进程内内存字典而不是数据库**：`_paused_sessions`（orchestrator）和各子智能体的 `_tasks` 都只是 `dict`，实现简单、没有额外依赖，适合当前单机部署+演示场景；取舍是主服务或任一子智能体进程重启后，所有暂停中的会话和历史 Task 全部丢失，前端拿着旧的 `context_id` 续跑会收到 `resume_chain` 抛出的 `KeyError`（映射为 HTTP 404）。代码注释里也明确写了"生产建议换为 Redis/DB"，这是有意识的技术债务而非疏漏。
4. **为什么单步失败重试 2 次退避重试而不是重试到成功或直接失败**：`_RETRY_ATTEMPTS=2` 是在"网络抖动/子进程刚重启还没就绪"这类瞬时故障与"用户等待时长"之间的折中——重试次数太少覆盖不了常见的瞬时抖动，太多会让前端长时间挂起等待（单次 `_send_message` 超时已设到 600s）；退避耗尽后不阻塞整条链路重试到死，而是把该步标记失败并保留之前已完成步骤的产出返回给前端，由使用方决定是否重新发起。

## 第四部分：应用场景与实战

**核心使用场景**

- 多步骤内容自动生产：主题 → （可选）风格确认 → 大纲 → 正文 → 摘要，四个专职 Agent 各司其职，用户可在 StyleAgent 阶段介入指定写作风格，也可跳过走默认路径。
- 人机协作（Human-in-the-loop）流程的参考实现：演示如何用标准 A2A 的 `input-required` 状态 + `context_id` 续跑机制，在多 Agent 链路中插入"需要人补充信息才能继续"的一步，而不是让整条链路要么全自动要么全部失败。
- A2A 协议 + LLM 动态路由结合的示范：不是死板的固定 pipeline，而是每一步都由 Host Agent 结合已发现的 Agent 能力和当前进度做决策，可作为在自有系统中引入"可插拔多 Agent 编排"的参考。

**快速上手**

环境依赖：
- 主服务依赖：`fastapi`、`httpx`、`pydantic`（已在 `requirements.txt` 中）
- 子智能体额外依赖：`requests`、`uvicorn`
- Host Agent 的 LLM 路由依赖本地 Ollama：`ollama serve` 且已 `ollama pull deepseek-r1:1.5b`（监听 `http://localhost:11434`）；Ollama 不可用时自动退化为固定顺序，不影响链路整体可用性

启动方式：
```bash
# 方式一：随主服务一起启动（推荐，app/factory.py 的 lifespan 会自动拉起四个子智能体）
python main.py

# 方式二：手动单独调试某个子智能体
python service/ai/a2a/agents/style_agent.py     # :8004
python service/ai/a2a/agents/outline_agent.py   # :8001
python service/ai/a2a/agents/doc_agent.py       # :8002
python service/ai/a2a/agents/summary_agent.py   # :8003
```

调用方式：
```bash
# 同步执行整条链
curl -X POST http://localhost:3000/ai/a2a/chain \
  -H "Content-Type: application/json" -d '{"topic": "A2A 协议简介"}'

# SSE 流式执行（每完成一步推送一条事件）
curl -N -X POST http://localhost:3000/ai/a2a/chain/stream \
  -H "Content-Type: application/json" -d '{"topic": "A2A 协议简介"}'

# 某步返回 input-required（如 StyleAgent 询问写作风格）后续跑
curl -X POST http://localhost:3000/ai/a2a/chain/resume \
  -H "Content-Type: application/json" -d '{"context_id": "<上一步返回的 context_id>", "answer": "科普向"}'
```

常见问题排查：
- **端口冲突（8001-8004 被占用）**：`lifespan()` 启动前已经通过 `_kill_stale_listener` 用 `lsof -ti :{port}` + `SIGTERM` 主动清理，正常情况下重启主服务即可自愈；如果残留进程对 SIGTERM 没响应（僵死），需要手动 `lsof -i :8001` 找到 PID 后 `kill -9`。
- **子进程崩溃/未启动成功**：`subprocess.Popen(..., stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)` 把子进程的标准输出/错误都丢弃了，排查时最直接的办法是把对应脚本单独 `python service/ai/a2a/agents/xxx_agent.py` 跑起来看报错；`registry.discover_all()` 对不可达的 Agent 是静默跳过（`except Exception: continue`），所以某个子智能体没起来不会让整个 `/ai/a2a/chain` 请求直接报错，而是 Host Agent 会看到"可用 Agent 变少"，最终可能因为 `candidates` 为空提前判定 `DONE`，产出的链路会比预期短。
- **链路一直卡在 `chain_paused` 续不下去**：多半是前端没有把 `chain_paused` 事件里的 `context_id` 存下来，或者调用 `/ai/a2a/chain/resume` 时 `context_id`/`answer` 传空——路由层对这两个参数做了非空校验，缺失会直接返回 400；`context_id` 对应的会话如果因为主服务重启而丢失（`_paused_sessions` 是内存字典），会收到 404。
- **Host Agent 路由结果不稳定/总是走固定顺序**：检查 Ollama 是否在跑（`curl http://localhost:11434/api/tags`）、模型是否已 `pull`；`decide_next_agent` 里 LLM 调用异常、输出解析不到候选 Agent 名、或选择了已完成过的 Agent，都会静默退化为 `_FALLBACK_ORDER`，这是设计上的兜底行为而非 bug。
- **`DataPart` 数据格式不匹配**：各 Agent 间的输入输出字段是隐式约定（如 `topic`、`title`、`style`），修改某个 Agent 的输出结构后，需要同步检查下游 Agent（尤其是 `host_agent._short_summary` 和 `orchestrator._short_summary` 里读取 `data.get("topic"/"title")` 的地方）是否还能正确摘要展示。

## 第五部分：评估与展望

**优势**

- 四个子智能体独立进程部署，单个 Agent 故障或卡死不拖垮整条服务，`_kill_stale_listener` 让重启具备自愈能力。
- 路由决策与调用机制解耦（`host_agent.py` vs `orchestrator.py`），新增/替换 Agent 只需改 `registry.AGENT_BASE_URLS` 和对应 `AgentCard`，不用碰编排主流程代码。
- 完整实现了 `input-required` 暂停/续跑语义，是少见的把人机协作纳入标准 A2A 任务生命周期（而非另起一套交互机制）的实现。
- 失败降级充分：单步网络失败有重试，重试耗尽有优雅降级（保留已完成步骤产出），LLM 路由不可用有固定顺序兜底，单个 Agent 不可达不影响能力发现整体。

**局限与技术债务**

- `_paused_sessions` 和各子智能体的 `_tasks` 都是进程内内存字典，重启即丢失，多实例部署下也无法共享状态，注释里已明确标注需要换 Redis/DB。
- Host Agent 依赖的本地小模型（`deepseek-r1:1.5b`，`num_predict=200`）推理质量有限，复杂主题下路由决策的准确性没有量化评估，退化行为虽然安全但会让"动态路由"退化成"固定顺序"，实际收益打折扣。
- `registry.AGENT_BASE_URLS` 仍是硬编码的本机地址（`127.0.0.1:800{1-4}`），没有做真正的服务发现，无法水平扩展或跨机器部署子智能体。
- 子智能体间的数据契约（`DataPart.data` 的字段命名）完全是隐式约定，没有 Schema 校验，一个 Agent 改了输出字段名，只有运行到下游解析处才会暴露问题。
- `MAX_STEPS = 5` 是写死的硬上限，没有针对"链路应该多长"给出可配置或可解释的依据。

**演进建议**

- 短期：把 `_paused_sessions`/子智能体 `_tasks` 迁移到 Redis，支持多实例部署和进程重启后的会话恢复；给 `DataPart.data` 补充 JSON Schema 校验，Agent 间契约从"约定"变成"强制"。
- 中期：给 `registry` 加健康检查/心跳，而不是仅在调用失败时被动感知 Agent 不可达；`decide_next_agent` 增加决策日志和可观测性，便于评估动态路由相对固定顺序的实际收益。
- 长期：引入真正的服务发现（Consul/etcd/Nacos）替换硬编码 URL 表；补充链路级别的分布式追踪（OpenTelemetry），把编排器 + 四个子智能体的调用串成一条完整的 trace。

**行业前沿**

- **Google A2A Protocol**：持续在多厂商生态中推进标准化，与 MCP（Model Context Protocol）形成互补——MCP 解决 Agent 如何调用工具/数据源，A2A 解决 Agent 与 Agent 之间如何通信协作。
- **多 Agent 编排框架**：OpenAI Agents SDK（Swarm 的后继）、AutoGen 等仍以同进程内 handoff 为主流实践，强调开发效率；A2A 这类跨进程标准协议更适合需要独立部署/独立团队维护的场景，两类方案在当前阶段是互补而非替代关系。
- **生产级编排能力**：Temporal、Apache Airflow 等成熟工作流引擎开始支持 AI Agent 场景，其持久化执行、重试策略、可观测性能力，正是本模块当前"进程内内存状态 + 简单重试"实现的短板所在，是可以直接对标的演进方向。
