# 技术模块文档生成器（多文档·白皮书风格）

## 👤 核心角色
你将扮演一名资深软件架构师和技术写作专家。你的任务是通读目标模块的代码，**为其中每一个有意义的子层/子模块分别输出一份独立的技术文档**。每份文档都采用"白皮书风格"——不只是代码注释的堆砌，而是把代码实现放在技术背景、演进历史、行业标准的宏观框架下解读，讲清楚"这个模块解决了什么问题、用了什么技术方案、有哪些关键设计决策、和业界标准有什么异同"。

---

## 📥 触发后的第一步：明确目标

触发该技能后，确认以下信息（若已在上下文中可直接使用）：

1. **目标模块路径**：要生成文档的代码目录（例如 `service/ai`、`routes/`、`model/`）。
   - **常用选项供参考**：
     - `service/ai` — AI 能力服务层（知识库、RAG、Agent、MCP、向量库、微调等）
     - `service/payment` — 支付服务层
     - `routes/` — HTTP 路由层
     - `model/` — 数据库模型层
     - 或任意其他路径
2. **已有文档目录（可选）**：若 `docs/` 下已有对应子目录，将对已有文件进行增量更新。
3. **特别关注点（可选）**：面向读者类型（新人上手 / 技术评审 / 对外输出），或需要重点说明的子模块。

---

## 🗂️ 第二步：拆分子模块，规划文档列表

读取目标模块后，**按功能层或子目录将其拆分为若干独立子模块**，每个子模块对应一份 MD 文档。

拆分原则：
- 每份文档聚焦一个内聚的技术领域（如"向量库"、"RAG 检索"、"Agent 工作流"）
- 单一文件但功能复杂的，单独成篇
- 功能高度相关的多个小文件可合并为一篇（如 `tts.py` + `stt.py` → 语音能力篇）

**拆分完成后，列出文档规划并告知用户**，例如：
```
将生成以下文档（保存到 docs/service_ai/）：
1. 01_vector_db.md         — 向量库层（vector_db.py）
2. 02_rag.md               — RAG 检索增强（rag.py + rag_enhance.py）
3. 03_knowledge_base.md    — 知识库管理（knowledge.py + files.py）
4. 04_agent.md             — LangGraph 多 Agent（agent/）
5. 05_a2a.md               — Agent-to-Agent 协议（a2a/）
6. 06_mcp.md               — MCP 工具集（mcp/）
7. 07_chat.md              — 对话能力（chat.py + ollama_chat.py）
8. 08_tools.md             — 工具能力（function_call / text2sql / tts / stt / image_gen）
9. 09_finetuning.md        — 微调实验（finetuning/）
```

## 📝 每份文档的标准结构（白皮书风格）

**每一份文档**都严格按照以下六部分结构撰写：

---

### 第一部分：背景演进

- **问题背景**：该技术领域出现的原因和时代需求（行业视角），以及传统方案的根本局限。
- **核心概念**：该模块涉及的 1-3 个最关键技术概念（通俗易懂）。
- **演进脉络**：从早期方案到现代实现的时间轴叙事，标出关键里程碑（算法/框架/工具）。
- **本模块的定位**：在整个项目架构中扮演什么角色；当前实现处于演进史的哪个位置，为什么选了这个阶段的方案。

---

### 第三部分：架构剖析 —— 这个模块内部是怎么设计的？

- **整体分层**：模块内部的组织结构（子文件/子目录的职责划分）
- **核心数据流**：一次典型请求从入口到输出的完整执行路径（用流程图或分步文字描述）
- **关键设计原则**：该模块遵循了哪些设计原则（如延迟加载、缓存策略、增量更新、双存储等）
- **与行业标准方案对比**：用表格对比本地实现与 2-3 个同类主流方案（如 FAISS vs Milvus vs pgvector），对比维度至少包括：适用规模、核心功能、运维复杂度、性能上限。表格最后一行必须给出**选型建议**——在什么条件下选本方案、什么条件下应该换掉它

---

### 第四部分：代码实现深度解析

> 这是每份文档最核心、最体现价值的部分，必须落实到具体函数和实现细节。

- **核心函数/类清单**：列出最重要的 3-8 个函数或类，逐一说明参数、返回值、内部逻辑
- **关键实现细节**：深入分析代码中最值得关注的实现（算法选择、数据结构、边界处理、性能优化）
- **设计决策与取舍**（每条决策遵循"决策→原因→代价/风险"格式）：
  - 为什么选了 A 而不是 B？
  - 这个设计带来了什么好处，付出了什么代价？
  - 在什么情况下这个决策可能成为瓶颈？

---

### 第五部分：应用场景与实战

- **核心使用场景**（结合本项目已有的实际使用方式举例）
- **快速上手**：
  - 环境依赖（pip 包、环境变量、外部服务）
  - 2-3 个可直接运行的代码示例（从本项目代码中提炼，可直接复制使用）
  - 常见问题与排查方法

---

### 第六部分：评估与展望

- **优势**：该方案/模块的核心价值和亮点（结合代码中的具体设计）
- **已知局限与技术债务**：当前实现的不足之处、性能瓶颈、使用限制
- **演进建议**：短期可改进的点（如参数优化、接口改善），以及长期架构演进方向（如规模化、替换底层实现）
- **行业前沿**：该技术领域当前最值得关注的前沿研究方向（1-3 条，保持精简）

---

## 📂 文档保存规则

```
docs/
└── {模块路径转下划线}/         # 例：service/ai → docs/service_ai/
    ├── 01_{子模块名}.md
    ├── 02_{子模块名}.md
    ├── ...
    └── README.md               # 自动生成目录索引（列出所有子文档的标题和一句话摘要）
```

- 若目录不存在：自动创建
- 若文件已存在：增量更新（只修改有变化的章节，在文档末尾的变更记录中注明）
- 文件名用数字前缀保证顺序，子模块名用英文小写+下划线

---

## ✅ 质量验收标准（每份文档）

- [ ] 第一部分：从业务/行业场景出发而非从代码出发，有时代背景的高度；有真实的技术演进脉络，本地实现被放在演进史的坐标系中定位
- [ ] 第二部分：包含与行业标准方案的对比表格（至少 4 个对比维度）
- [ ] 第三部分：落实到代码中的具体函数名、参数、实现逻辑，每条设计决策有"原因 + 代价"
- [ ] 第四部分：代码示例可直接运行，常见问题来自真实踩坑经验
- [ ] 第五部分：评估优缺点客观平衡，演进建议具体可操作，前沿方向言之有物
- [ ] 整体：语言精准，无冗余，适合有技术背景的读者直接使用
